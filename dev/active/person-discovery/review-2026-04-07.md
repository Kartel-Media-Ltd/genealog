## 2. Nowe problemy

### 🔴 B4 — Race condition w `GlobalIndexService::indexPerson` — brak ON DUPLICATE KEY
**Plik:** `src/Services/Discovery/GlobalIndexService.php:92-123`

```php
$existing = $this->db->fetchOne('SELECT id FROM global_person_index WHERE person_id = ?', ...);
if ($existing) {
    // UPDATE
} else {
    // INSERT — race condition tutaj
}
```

**Problem:** Przy równoczesnych requestach (np. `bin/reindex-all.php` + EventDispatcher emit z nowego create) oba procesy wykonają `SELECT` przed `INSERT` i dostaną `NULL` → oba próbują INSERT → `Duplicate entry for key 'uq_gpi_person'` → nieobsługiwany `PDOException`. EventDispatcher pochłania wyjątki (EventDispatcher.php:45), więc nie crashuje requestu, ale wpis nie zostanie zapisany + cichy błąd w logach.

**Naprawa:**
```sql
INSERT INTO global_person_index (id, fingerprint_hash, name_soundex, ...)
VALUES (?, ?, ?, ...)
ON DUPLICATE KEY UPDATE
    fingerprint_hash = VALUES(fingerprint_hash),
    name_soundex = VALUES(name_soundex),
    tree_id = VALUES(tree_id),
    owner_user_id = VALUES(owner_user_id),
    region = VALUES(region),
    earliest_birth_year = VALUES(earliest_birth_year),
    latest_birth_year = VALUES(latest_birth_year)
```

### 🔴 B5 — `PersonImportService::importFromMatch` — brak transakcji
**Plik:** `src/Services/Discovery/PersonImportService.php:42-78`

Sekwencja:
1. `updateStatusIfPending` (UPDATE)
2. `personService->create` (INSERT)
3. `logAudit` (INSERT)

**Problem:** Brak transakcji. Jeśli krok 2 zakończy się błędem DB po udanym kroku 1, sugestia pozostaje oznaczona `imported`, ale osoba nie powstała w bazie. Stan nieodwracalnie niespójny — user nie może ponowić (status ≠ pending).

**Naprawa:**
```php
$this->db->beginTransaction();
try {
    $affected = $this->repo->updateStatusIfPending(...);
    if ($affected === 0) {
        $this->db->rollBack();
        throw new \RuntimeException('Ta propozycja została już zaakceptowana...');
    }
    $person = $this->personService->create(...);
    $this->repo->logAudit(...);
    $this->db->commit();
    return $person->id;
} catch (\Throwable $e) {
    $this->db->rollBack();
    throw $e;
}
```

### 🟠 I7 — `updateSettings` — pominięty unindex gdy `userOptIn` = 0
**Plik:** `src/Controllers/DiscoveryController.php:259-263`

```php
if ($treeOptIn && $userOptIn) {
    $this->globalIndex->reindexTree($treeId);
} elseif ($previously && !$treeOptIn) {
    EventDispatcher::emit('tree.indexed_globally.disabled', $treeId);
}
```

**Problem:** Scenariusz: `treeOptIn=1`, `previously=1`, user zmienia `userOptIn` z `1` na `0`. Żadna gałąź nie odpali (`$treeOptIn && $userOptIn` = false, `$previously && !$treeOptIn` = false). Osoby pozostają w `global_person_index` mimo wycofanej zgody konta. **Naruszenie RODO Art. 7(3) — right to withdraw consent.**

**Naprawa:** trzecia gałąź `elseif ($previously && !$userOptIn) { $this->globalIndex->unindexTree($treeId); }` — LUB refactor do jawnego sprawdzenia aktualnej kwalifikacji (isEligible) niezależnie od poprzedniego stanu.

### 🟠 I8 — `DiscoveryController::search` — brak guard clause dla pustego `userId`
**Plik:** `src/Controllers/DiscoveryController.php:49`

$userId = (string)Session::get('user_id');

### 🟠 I9 — `CrossTreeMatchSource` JOIN na `persons` ujawnia imię/nazwisko
**Plik:** `src/Services/Discovery/Sources/CrossTreeMatchSource.php:86-95`

```sql
SELECT gpi.id AS gpi_id, ..., p.first_name, p.last_name
FROM global_person_index gpi
JOIN persons p ON p.id = gpi.person_id
```

**Problem:** Kontekst P4 z wstępnego audytu to było `tree_name` → `treeRef` (anonimowy hash). Ale `first_name` i `last_name` nadal są JOIN'owane z `persons` i trafiają do JSON response. Jeśli user zmieni `visibility` osoby z powrotem na `private` po zaindeksowaniu, a `global_person_index` nie został jeszcze zaktualizowany (poprzez unindex), cross-tree query zwróci AKTUALNE imię/nazwisko z `persons`. To ryzyko RODO.

**Świadoma decyzja czy bug?** Imię/nazwisko MUSI być w cross-tree response żeby user rozpoznał dopasowanie. Ale powinny pochodzić z `global_person_index` (zamrożone w momencie indeksowania), nie z `persons` (mutowalne).

**Naprawa:** zgodna z I2 z poprzedniego review — dodać `first_name`, `last_name` do `global_person_index` (migracja 009) i zapisywać przy indexPerson. CrossTreeMatchSource używa `gpi.first_name/last_name` bez JOIN.

Polling co 30s nie zatrzymuje się gdy karta jest ukryta — zużywa baterię na mobile. Dodać:

document.addEventListener('visibilitychange', () => {

## 3. ✅ Pozytywne

- **5 warunków RODO w `isEligible`** — wzorcowa kolejność: żyjące → visibility → tree opt-in → user opt-in → 100 lat
- **`MatchResult::jsonSerialize` switch per sourceType** — czysta anonimizacja cross-tree na poziomie serializacji
- **Optimistic lock w `PersonImportService`** — dobra technika, jeśli tylko owinąć w transakcję (patrz B5)
- **`FingerprintService::transliterate`** — iconv + fallback mapa polskich liter, defense in depth
- **`EventDispatcher::emit`** pochłania wyjątki z logowaniem — systemy indeksowania nie blokują operacji głównej
- **CSRF na wszystkich POST** `DiscoveryController` — weryfikowane
- **`discoveryConsentAt`** zapisywane poprawnie przez `CASE WHEN` w SQL przy pierwszym opt-in
- **Hybrid matching strategy** — exact fingerprint → fuzzy fallback z confidence threshold 0.5, cap 0.95
- **Polish Soundex** — `iconv ASCII//TRANSLIT//IGNORE` przed `soundex()` + fallback mapa
- **`x-cloak` + `x-transition`** — brak flash of unstyled content w Alpine panelach
- **Debounce 400ms** + min 2 znaki — poprawne warunki frontend i backend
