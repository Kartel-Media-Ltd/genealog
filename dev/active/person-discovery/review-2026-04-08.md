# Code Review — Person Discovery (2026-04-08)

**Werdykt:** ⚠️ **PASS WITH BLOCKING ISSUES** — 6 blocking, 10 important, 13 nit, 10 suggestions

## Podsumowanie

Feature Person Discovery jest architektonicznie solidny — separacja źródeł przez `MatchSourceInterface`, EventDispatcher dla hooks, disciplined RODO compliance w `GlobalIndexService`. Jednak są **dwa blocking buggy w najnowszym dodatku** (panel "Możliwe powiązania"): brakujące persistowanie sugestii (cały panel = dead code) oraz CSRF token rotation race (drugi click = 403). Anonimizacja cross-tree w `MatchResult::jsonSerialize` jest dobrze zaimplementowana.

## 🔴 Blocking (6)

### B1: `person_match_suggestions` nigdy nie jest zapisywane
**Plik:** `src/Services/Discovery/MatchingService.php:89-153` + `src/Repositories/DiscoveryRepository.php:21-50`

`DiscoveryRepository::saveSuggestion()` jest zdefiniowany ale **nie wywołany z żadnego miejsca w kodzie** (potwierdzone grep). Panel "Możliwe powiązania" w `show.php` czyta `findPendingForPerson()` — który zawsze zwróci pustą listę. **Cały panel jest nieosiągalny przez normalny flow**.

`findAndNotifyMatches()` robi tylko `notifications->notifyPersonMatch()` bez persystencji.

**Fix:** Dodać `$this->repo->saveSuggestion(...)` w pętli po `$matches` w `MatchingService::findAndNotifyMatches` PRZED emit notyfikacji — żeby każdy cross-tree match był persystowany.

### B2: CSRF token rotation race — drugi accept/reject zawsze daje 403
**Plik:** `src/views/pages/trees/persons/show.php:282-319`

`Csrf::verify()` przy sukcesie UNSETuje stary token i generuje nowy (`Csrf.php:27-34`). Meta tag jest czytany bezpośrednio z DOM-u (`document.querySelector('meta[name="csrf-token"]')?.content`) i **nigdy nie jest aktualizowany** po udanym requeście — w odróżnieniu od `NotificationController` (zwraca `csrf` w JSON i bell aktualizuje meta tag).

Efekt: pierwszy click działa, drugi → `HTTP 403 — CSRF token mismatch`.

**Fix:**
1. `DiscoveryController::importMatch` i `rejectMatch` muszą zwracać `['ok' => true, 'csrf' => Csrf::getToken()]`
2. Frontend w `acceptMatch`/`rejectMatch` po udanym requeście aktualizować `meta[name=csrf-token]` na podstawie response JSON

---

### B3: importMatch tworzy duplikat osoby zamiast relacji dla local match
**Plik:** `src/Controllers/DiscoveryController.php:121-161`

Kod robi `SELECT tree_id FROM persons WHERE id = ?` dla `suggestion.person_id` (osoba w drzewie usera) i tworzy NOWĄ osobę w tym samym drzewie. Dla cross-tree matchu poprawne. **Dla `source_type='local'` to znaczy że user otrzyma duplikat osoby Y w drzewie X** — bez sprawdzenia czy to ma sens.

Brak walidacji `suggestion.source_type`. Brak endpointu `/api/discovery/match/{id}` mimo komentarza w kodzie.

**Fix:** Zablokować `importMatch` dla `source_type='local'` (właściwym działaniem jest dodanie relacji, nie duplikacji), lub przynajmniej zweryfikować że `sourceData` ma kompletne pola.

### B4: PersonImportService — birth_place gubione przy cross-tree import
**Plik:** `src/Services/Discovery/PersonImportService.php:49`

`'birth_date' => !empty($sourceData['birthYear']) ? (string)$sourceData['birthYear'] : ''` — przekazuje `"1945"` jako `birth_date`. Następnie `sanitizeDate('1945')` → `"1945-01-01"`. OK, ale dla cross-tree matchu `source_data` ma tylko `{region, treeRef}` — brak `birthPlace`. Import traci całą informację o regionie bo service nie mapuje `region` → `birth_place`.

**Fix:** Zmapować `sourceData['region']` → `birth_place` gdy brak `birthPlace`.

---

### B5: PersonImportService — race condition + brak rollback w niektórych ścieżkach
**Plik:** `src/Services/Discovery/PersonImportService.php:87-95`

`beginTransaction()` otwiera transakcję, `updateStatusIfPending` bierze lock, ale `PersonService::create` wewnątrz emituje `person.created` event który wywołuje `findAndNotifyMatches` → robi SELECT z `global_person_index` i potencjalnie INSERT do `notifications`. **Wszystko w tej samej transakcji**.

Catch `\RuntimeException` re-throw bez rollback (komentarz "już wywołany" — ale tylko dla affected===0). Jeśli `personService->create()` lub `logAudit()` rzuci RuntimeException, transakcja **nie jest rollbackowana**.

**Fix:** Ujednolicić catch — zawsze sprawdzić `inTransaction()` przed rollback.

---

### B6: CrossTreeMatchSource — soundex-only match z confidence 0.6 dla popularnych nazwisk
**Plik:** `src/Services/Discovery/Sources/CrossTreeMatchSource.php:53-73`

Linia 70 dołącza `gpi.name_soundex = ?` jako OR-warunek. Linia 109 ustawia `confidence = 0.6` dla soundex match (wyższe niż `LocalTreeMatchSource::MIN_FUZZY = 0.5`!). **Przy popularnych polskich nazwiskach ("Kowalski", "Nowak") zwróci 20 fałszywych dopasowań** z 60% confidence. User widzi "60% średnie" w badge i myśli że to prawdziwe powiązanie. Mocno zanieczyści UI.

**Fix:** (a) Confidence dla soundex-only = 0.3, odrzucić < 0.5; LUB (b) wymagać dodatkowo `earliest_birth_year BETWEEN ? AND ?` dla soundex match.

## 🔵 Suggestions (10)

- 🔵 **Brak testów Discovery** — `tests/Unit/` nie zawiera żadnego testu dla `FingerprintService`, `GlobalIndexService`, `MatchingService`. FingerprintService jest deterministyczny → łatwe pełne pokrycie
- 🔵 **`MatchResult` powinien mieć `sourceLabel`** — frontend nie powinien hardkodować mapowania
- 🔵 **Brak `Retry-After` header w 429 response** dla rate limit
- 🔵 **Brak logowania `cross_tree_query` w audit log** dla każdego search (RODO Art. 30)
- 🔵 **`EventDispatcher::emit` synchroniczny** — przy bulk GEDCOM 1000 osób blokuje request; rozważyć kolejkę
- 🔵 **Confidence threshold per source** — `MatchSourceInterface::MIN_CONFIDENCE` zamiast hardcoded 0.5/0.6
- 🔵 **`FingerprintService::compute()` powinno przyjmować `?string $region`** zamiast pełnego array
- 🔵 **Debounce na `birth_place`** w autosuggest create.php (zawęza wyniki gdy user wpisze miasto)
- 🔵 **`hidden_for_query` w sessionStorage** dla autosuggest UX
- 🔵 **`CrossTreeMatchSource` nie loguje** liczby zwróconych matchy per query (debugging)

## ✅ Co działa dobrze

- **Privacy by Design w `MatchResult::jsonSerialize`** — pojedyncza funkcja do audytu, dla cross_tree zwraca TYLKO `firstName, lastName, birthYear, region, treeRef, confidence`
- **Immutable names w `global_person_index` (migration 009)** — zamrożenie PII przy indeksowaniu
- **`isEligible()` w GlobalIndexService** enforcuje WSZYSTKIE 5 reguł RODO (defense in depth)
- **`INSERT...ON DUPLICATE KEY UPDATE` z UNIQUE KEY** — atomowa upsert, race-safe
- **Optimistic lock w `PersonImportService::updateStatusIfPending`** — idempotentny import
- **Rate limiter 30 req/min** na `/api/discovery/search` — anti-enumeration
- **IDOR prevention** w `findPendingForPerson`, `findById` — `created_for_user = $userId`
- **CSRF verification** na wszystkich POST endpoints
- **`source_audit_log` z ON DELETE SET NULL** — RODO Art. 17 + Art. 30 compliant
- **Wykluczenie `accessibleTreeIds` w CrossTreeMatchSource** — brak self-matchów
- **Separation of concerns w `MatchSourceInterface`** — clean architecture
- **EventDispatcher swallow exceptions** — listener crash nie blokuje `PersonService::create`
- **Warunkowa rejestracja external sources** przez env vars + `isAvailable()`
- **Idempotent migracje** (008, 009) z `IF NOT EXISTS`
- **Transliteracja polskich diakrytyków** przed levenshtein
- **Bell notification pause przy `visibilitychange`** — battery saver mobile
