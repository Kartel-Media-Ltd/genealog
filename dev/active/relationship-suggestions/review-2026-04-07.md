## 🔴 BLOCKING

### [B1] GedcomService::export() — properties w snake_case (silent NULL)
**Plik:** `src/Services/GedcomService.php:450, 452, 464, 465, 477, 481, 482`

Model `Relationship` używa camelCase (`personAId`, `personBId`, `startDate`), ale `export()` odwołuje się do `$rel->person_a_id`, `$rel->person_b_id`, `$spouseRel->start_date`. PHP 8 z `readonly` properties zwróci `null` cicho (a nie rzuci). Efekt: GEDCOM eksport produkuje pusty `$parentToChildren` → wszystkie FAM bez `CHIL`.

**Naprawa:** zmienić wszystkie 6 wystąpień na camelCase: `personAId`, `personBId`, `startDate`.

> **Uwaga historyczna:** ten bug istniał już przed naszymi zmianami semantyki — nie wprowadzony przez `relationship-suggestions`, ale ujawniony przez review.

### [B2] GedcomService::export() — duplikaty CHIL przez forward+inverse
**Plik:** `src/Services/GedcomService.php:447-454`

`RelationshipService::create()` zawsze tworzy obie strony: `('parent', A, B)` ORAZ `('child', B, A)`. Pętla w `export()` iteruje obie i dodaje do `$parentToChildren` dwa razy → w GEDCOM `CHIL` pojawi się dwukrotnie.

**Naprawa:** użyj seta lub przetwarzaj tylko jeden typ:
```php
foreach ($relationships as $rel) {
    if ($rel->type === 'child') {
        $parentToChildren[$rel->personAId][$rel->personBId] = true;
    }
}
// potem array_keys()
```

### [B3] SuggestionService — case 'child' sugeruje fałszywe dzieci
**Plik:** `src/Services/SuggestionService.php:104-114`

```php
case 'child':  // $otherId = B = A's child
    foreach ($otherRels as $or) {
        if ($or->type === 'sibling') {
            $this->addSuggestion(..., 'child', $or->personBId, ...);
        }
```

Sugeruje rodzeństwo dziecka B jako WŁASNE dziecko A. Ale rodzeństwo B może być dzieckiem **innego związku** B (np. z poprzedniego małżeństwa) — wtedy NIE jest dzieckiem A. Brak weryfikacji `relRepo->exists($candidateSibling, $personId, 'parent', $treeId)`.

**Naprawa:** dodać check, że rodzeństwo dziecka ma `personId` (A) jako rodzica.

### [B4] show.php — typeLabel parent↔child jest odwrócone
**Plik:** `src/views/pages/trees/persons/show.php:186-193`

```php
$typeLabel = match($s['type']) {
    'child'   => 'rodzic',   // ❌ powinno być 'dziecko'
    'parent'  => 'dziecko',  // ❌ powinno być 'rodzic'
```

W FORM-interp: sugestia `type='parent'` znaczy "B jest rodzicem A" → label = "rodzic". Tu jest na odwrót, użytkownik widzi: "sugeruję X jako **dziecko**" gdy X jest rodzicem.

**Naprawa:** zamienić: `'child' => 'dziecko'`, `'parent' => 'rodzic'`.

## 🟠 IMPORTANT

### [I1] SuggestionController — catch InvalidArgumentException połyka błędy walidacji
**Plik:** `src/Controllers/SuggestionController.php:74-76`

Catch bez powodu — użytkownik nie wie, czy sugestia została pominięta bo "już istnieje", "parent younger than child", czy "cykl". Komunikat "Nie dodano żadnych" jest mylący.

**Naprawa:** zbieraj odrzucone sugestie z powodami i pokazuj w flash, lub przynajmniej `error_log()`.

### [I2] GedcomService::importFamilies() — brak inverse 'spouse'
**Plik:** `src/Services/GedcomService.php:349-366`

Spouse jest dodawany tylko jednostronnie (`(aId, bId, 'spouse')`), brakuje `(bId, aId, 'spouse')`. Dla parent/child obie strony są dodawane ręcznie, ale dla spouse nie. `findByPerson(wife)` nie zwróci spouse-rel.

**Naprawa:** dodać drugi insert lub użyć `RelationshipService::create()`.

### [I3] RelationshipService — porównanie dat jako string
**Plik:** `src/Services/RelationshipService.php:55-59`

`$parent->birthDate > $child->birthDate` porównuje stringi leksykograficznie. Działa **przypadkowo** bo format `Y-m-d` jest sortable, ale jeśli kiedykolwiek wpadnie data w innym formacie → bug.

**Naprawa:** `substr($date, 0, 4) > substr(...)` jako int, lub `strtotime()`.

### [I4] SuggestionService — N+1 zapytań
**Plik:** `src/Services/SuggestionService.php:38-41, 52-56, 177`

Dla każdej osoby `findByPerson()` + dla każdej sugestii `relRepo->exists()` + `personRepo->findById()`. Drzewo 50 osób → 50+ zapytań. CLAUDE.md mówi że drzewa są małe, ale prosty cache w pamięci by to rozwiązał.

**Naprawa:** array cache na `findByPerson` w ramach jednego `compute()`.

### [I5] RelationshipController::showCreate() — wywołuje compute() przy każdym GET
**Plik:** `src/Controllers/RelationshipController.php:50-51`

```php
$suggestions = $this->suggestionService->compute($personId, $treeId);
```

Każde otwarcie formularza relacji odpala N+1 query. Jeśli `relationship-create.php` faktycznie używa sugestii — OK. Jeśli nie — zbędny koszt.

**Weryfikacja:** sprawdzić czy panel sugestii jest renderowany w `relationship-create.php`.

### [I6] ApiController — duplikacja linków sibling/spouse
**Plik:** `src/Controllers/ApiController.php:95-103`

Spouse/sibling/partner są tworzone z obu stron przez `RelationshipService` — ale `personsForTree()` iteruje wszystkie i dodaje do `$links` bez deduplikacji. D3 narysuje **dwie linie** między każdą parą małżonków. Dla `parent-extra` deduplikacja jest (`$parentSet`), tutaj brak.

**Naprawa:** filtruj `$rel->personAId < $rel->personBId` lub użyj seta po canonical pair.

### [I7] GedcomService::export() — brak `1 MARR` dla par bez daty ślubu
**Plik:** `src/Services/GedcomService.php:610-612`

```php
if ($family['start_date']) {
    $lines[] = '1 MARR';
```

GEDCOM 5.5.1 zaleca emitować `1 MARR` zawsze (bez `2 DATE` jeśli brak daty), żeby oznaczyć fakt małżeństwa. Inne narzędzia (Ancestry, MyHeritage) mogą nie rozpoznać pary bez `MARR`.

**Naprawa:** zawsze `1 MARR`, opcjonalnie `2 DATE`.

### [I8] Response chain `withFlash()->redirect()` — type system nie widzi `never`
**Plik:** `src/Controllers/SuggestionController.php:40-44` (i podobne w innych)

`Response::redirect()` to `never`, ale `withFlash()` zwraca `static`, więc analizator statyczny nie wie że dalsza ścieżka kodu jest nieosiągalna. Nie blocking (exit działa), ale ukrywa potencjalne null-deref.

**Naprawa (opcjonalna):** dodać `return;` po chainach lub przerobić chain na osobne wywołania.
